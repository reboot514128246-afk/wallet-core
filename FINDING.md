# Medium Finding: Validator Confusion / Signature Replay Bypass

## Description
A vulnerability exists in the `WalletCore` validation logic where a signature intended for one validator can be reused with another validator. This is because the `validator` address is not included in the EIP-712 typed data hash signed by the user.

Specifically, in `ValidationLogic._getValidationHash`, the `CALLS_TYPEHASH` includes the `wallet` address, `nonce`, and `calls`, but omits the `validator` address that is used to verify the signature in `executeWithValidator`.

## Impact
An attacker or a malicious relayer can bypass security restrictions enforced by custom validators. For example, if a user has a `DailyLimitValidator` to restrict spending, they might sign a transaction intending it to be validated by that contract. A relayer can take that same signature and call `executeWithValidator` using the built-in ECDSA validator (`address(1)`), which does not enforce the daily limit, thus bypassing the security control.

## Proof of Concept
The vulnerability is demonstrated in `test/ValidatorConfusionPoC.t.sol`.
1. Alice adds a `DailyLimitValidator`.
2. Alice signs a transaction for 5 ether (exceeding the 1 ether limit).
3. The signature hash generated by `getValidationTypedHash` only depends on the calls and nonce.
4. Bob (the relayer) calls `executeWithValidator` with Alice's signature but specifies `address(1)` as the validator.
5. The built-in validator verifies the signature against Alice's address and succeeds.
6. The transaction executes, bypassing the `DailyLimitValidator`.

## Recommendation
Include the `validator` address in the EIP-712 typed data hash.

Update the `Calls` typehash and the hashing logic in `ValidationLogic.sol`:
```solidity
keccak256("Calls(address wallet,address validator,uint256 nonce,bytes32[] calls)");
```
And update `getValidationTypedHash` to accept the `validator` address as an argument.
